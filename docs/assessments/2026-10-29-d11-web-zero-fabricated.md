**Adversarial finding (auth precedence):** `diabetes.api.main` mounts protected routes with `[HybridBearerAuth, SessionAuth()]`. An explicit invalid Authorization bearer could fall through to a valid unrelated Django session via `SessionAuth`, silently selecting cookie identity instead of rejecting the supplied bearer. A valid bearer takes precedence and sets `request.user`; a cookie-only request must continue functioning. Security correction `a732fc31c64f833f615786974889b2772c10f48c`: `amina.vercel_session_auth.SessionAuth._get_key` rejects session fallback whenever the `HTTP_AUTHORIZATION` header is present, before CSRF session processing. This preserves cookie-only session + CSRF behavior, rejects invalid explicit bearers rather than mixing identities, and does not mutate clinical records. The new `test_conflicting_cookie_and_bearer_never_fall_back` runs with synthetic A/B log records and asserts (a) valid bearer B plus cookie A yields B; (b) invalid bearer plus cookie A yields 401; (c) cookie A without Authorization still yields A. **New-HEAD CI must be checked independently; do not reuse baseline GREEN.**

## 2026-10-29 — RED root causes and final candidate under verification

**Backend contradicted authority (red at `54b057d6`, `27c120e3`, `518033b5`):** Django HTTP session A plus explicit bearer B had incorrectly returned HTTP 200 / patient A data. This is a **security blocker**, not an acceptable visual/test-only defect. GitHub logs show the test failed in both SQLite and PostgreSQL. Exact vendor django-ninja 1.7.3 `APIKeyBase.__call__` calls `authenticate(request, key)` even when `key=None`, while `SessionAuth.authenticate` ignores the key, explaining why merely filtering in `SessionAuth._get_key` did not work. In addition to the in-auth protections, `ExplicitBearerCookieIdentityMiddleware` now runs after Django authentication and before API routing. On `/api/v1/`, requests with an existing session cookie **and** explicit invalid/mismatched bearer are rejected 401 before reaching a clinical view; matching cookie/native bearer and cookie-only/bearer-only paths are preserved. Targeted adversarial GET and POST assert 401/no patient writes when credentials conflict. **This patch requires exact-final-head proof**; no validated security closure yet.

**Browser scope corrected (Web red `40936712913`):** The 18-state single CI run reached **16/18 PASS**, and the remaining two Arabic 1280×900 A logins returned **HTTP 429**. Root cause proved in `core/auth_abuse.py`: account-auth limit 10 login attempts / 600 seconds, IP limit 20 / 600 seconds. Reusing one fake patient A for 12 login attempts in one CI test exceeded the *intended* protection. No product limit changed, no retry bypass. The workflow now uses two independent ephemeral PostgreSQL/Flutter/Playwright jobs (`strategy.matrix.locale=[fr,ar]`) testing 9 browser states per job: each locale × three viewport sizes × genuine A→B→A. Separate FR/AR screenshot artifacts sum to the **same 18 requested states**, with each separate test job naturally below login limits. Script requires `D19_CI_LOCALE`.
